# Nivara cryptography

This document records what Nivara's cryptographic layer does, why it is shaped this way, and what
it explicitly does not protect against. It is the reference for reviewing the code in
`domain/security` and `data/security`.

## Scope

This layer provides the primitives later work build on: authenticated encryption, a versioned
envelope format, secure randomness, keys in the platform key store, key wrapping, credential-based
key derivation and the recovery foundation.

It does **not** include enrolment screens, credential verification, biometric authentication,
session policy, app locking or the vault. Those layers consume what is described here; they do not
extend it.

## Building blocks

| Concern | Choice | Where |
| --- | --- | --- |
| Randomness | `java.security.SecureRandom` (platform provider) | `SecureRandomGenerator` |
| Authenticated encryption | AES-256-GCM, 128-bit tag, random 96-bit nonce per operation | `JcaEncryptionService`, `EncryptedEnvelope` |
| Envelope format | Versioned, self-describing, purpose-bound (see [envelope-format.md](envelope-format.md)) | `EncryptedEnvelope` |
| Key protection | Keys never exported when they live in the Android Keystore | `AndroidKeystoreDeviceKeyStore` |
| Key wrapping | AES-256-GCM envelope for device keys; HKDF-SHA-256 keystream + HMAC-SHA-256 tag for in-process keys | `NivaraContentKeyWrapper`, `SealedKeyContainer` |
| Credential KDF | PBKDF2-HMAC-SHA-256, 600 000 iterations, 128-bit salt, 256-bit output | `Pbkdf2KeyDerivationService` |
| Key expansion | HKDF-SHA-256 (RFC 5869) | `Hkdf` |
| Recovery | Independent 256-bit recovery key sealing the same content key | `HkdfRecoveryKeyEnvelopeService` |

No cryptographic primitive is implemented in this project. Every algorithm comes from the platform
provider; the code here composes them and enforces the rules that are easy to get wrong.

## The key hierarchy

```
                    user credential                    recovery key
                          │                                 │
                    PBKDF2-HMAC-SHA-256                     │
                  (600k iterations, salt)             (256 random bits)
                          │                                 │
                    wrapping key ─────────┐        ┌─────────┘
                                          ▼        ▼
                                     content key (256 random bits)
                                          │
                          AES-256-GCM ────┴──── vault content, metadata,
                                                application security data
```

Reasons for this shape:

- **One content key.** Files are not encrypted under a credential. A credential protects exactly
  one wrapping; changing it re-wraps the content key instead of re-encrypting data.
- **Two independent protections.** A credential-derived key and a recovery key both wrap the same
  content key, so forgetting the credential does not lose the data — and a recovery key does not
  have to be derived from anything a user remembers.
- **A device key is an option, not a requirement.** Devices with a secure element can hold a key
  Nivara cannot export; that key is used to protect material that must survive without a
  credential.

## Purpose binding

Every encrypted value declares one purpose (`EncryptionContext`): vault content, vault metadata,
recovery envelope, application security data, key wrapping, or device-protected key material.

The purpose tag sits in the authenticated header. A ciphertext created for one purpose cannot be
accepted for another: if the tag byte is edited, either the parser refuses it (`ContextMismatch`)
or the authentication tag fails (`AuthenticationFailed`). Both behaviours are covered by tests, one
of which uses an envelope generated by an independent implementation.

## Versioning

The envelope and the sealed-key container both begin with:

```
magic (4 bytes) | version (1) | scheme/algorithm identifier | purpose | reserved (0)
```

Rules Nivara follows:

- Unknown version, scheme, algorithm or purpose are **hard failures**. There is no "try the old
  algorithm" path and no downgrade.
- Old versions stay readable: their parsers are kept while the format is documented, so data
  written today survives a format change.
- A new format is introduced by publishing a new version number with its own layout — see
  [envelope-format.md](envelope-format.md) for the exact procedure.
- The reserved byte must be zero and is validated, so v2 can use it without ambiguity.

## Randomness

Keys, nonces, salts, recovery keys and wrap nonces all come from `SecureRandomGenerator`, which
wraps the platform's `SecureRandom` (`/dev/urandom` backed on Android). Nothing in the security code
uses `java.util.Random`, a timestamp, a counter or a constant for a cryptographic value, and the
static checks in `tools/verify_nivara.py` fail the build if that changes.

Nonce policy per algorithm:

- AES-256-GCM: a fresh random 96-bit nonce per encryption, generated inside the encryption service.
  Callers cannot supply one through `EncryptionService`, which removes the possibility of reuse.
  The probability of a collision stays negligible well past the number of encryptions a single
  device will ever perform.
- The sealed-key container uses a fresh random 128-bit nonce as the HKDF salt, so two wrappings of
  the same key are unrelated.

## Key derivation (PBKDF2)

PBKDF2-HMAC-SHA-256 with 600 000 iterations, a 16-byte random salt and a 256-bit output. The
parameters are a stored value (`KeyDerivationConfig`) that travels with the data, so the work factor
can be raised for new data while old data stays readable.

Why PBKDF2 and not Argon2id: PBKDF2 is part of the platform provider, so it behaves identically from
API 28 to current Android with no native library, no NDK dependency and no additional attack
surface. Argon2id would resist GPU attacks better but requires bundling a native implementation,
which is a deliberate decision for later work if the threat model calls for it — not something to
smuggle into a foundation release.

Derivation always runs on `Dispatchers.Default`: the configured cost is deliberately hundreds of
milliseconds.

## Device keys (Android Keystore)

- Generated as AES-256-GCM keys, `PURPOSE_ENCRYPT or PURPOSE_DECRYPT`, randomised encryption
  required, no padding.
- Key material cannot leave the platform: `SecretKey.getEncoded()` is `null` for these keys, and
  Nivara never asks the platform to export one.
- `getOrCreateKey` never replaces an existing key. Losing a key is preferable to silently making
  existing data unreadable.
- Invalidation is handled explicitly: a key that the platform destroyed (screen lock removed, new
  biometric enrolled) reports `KeyUnavailable` or `KeyInvalidated`, and `isKeyUsable` detects
  invalidation by attempting a cipher initialisation — the only supported way to tell.

**Documented limitation.** Nivara does not *require* hardware-backed keys at this time. Some API 28
devices and most emulators cannot provide a hardware-backed AES key, and requiring it would make the
app refuse to run rather than degrade predictably. Nivara also does not request StrongBox: it exists
on only some API 28 hardware, and an automatic fallback would make the guarantee unreportable. Both
are explicit future decisions, not silent downgrades.

**Documented trade-off.** Device keys disappear when the user removes their screen lock. That is the
platform protecting the key it can no longer protect, and it is why the design never depends on a
device key alone for data that must survive.

## Secret handling

- Secrets live in `SensitiveBytes`, which offers explicit `clear()` and a `REDACTED` `toString`.
- Credentials are `CharArray`s handed straight to `PBEKeySpec`; the spec's copy is cleared in a
  `finally` block. A credential is never converted to `String`.
- Temporary buffers (wrapping key copies, HKDF subkeys, derived keystreams) are cleared in `finally`
  blocks. Ciphertexts and nonces are not secret and are not cleared.
- `EncryptionService.encrypt(clearPlaintextAfterUse = true)` overwrites the caller's buffer, but only
  after the ciphertext exists, so a failed operation does not destroy the caller's data.
- Nothing in the security code logs, prints or includes key material in an exception message.
  Failures are fixed, non-descriptive strings.

**Honest limitation — erasure is best effort.** On a managed runtime (ART/JVM) you cannot prove a
secret is gone. The garbage collector may copy an array while compacting, the JIT may keep values in
registers or on the stack, a copy may live inside a `SecretKeySpec`, and the platform may have paged
memory to disk before `clear()` ran. Clearing the live buffer narrows the window; it does not close
it. Nivara therefore also limits *lifetime*: keys derived from a credential exist only while
unlocking, and the recovery key is shown once and then cleared. Nivara claims no more than this.

## Threat model

Nivara's cryptography protects against:

- another application on the device reading Nivara's stored data;
- a person who gains access to Nivara's files without the credential or recovery key;
- offline analysis of a copied file set, including backup images (backup is disabled entirely);
- tampering: modified data is rejected, not silently accepted.

It does not protect against:

- a rooted or compromised device, or a malicious operating system;
- a privileged attacker who can read process memory while a key is in use;
- someone who obtains both the recovery envelope **and** the recovery key (they must never be kept
  together);
- coercion, physical extraction or hardware attacks on the secure element beyond its own guarantees;
- a weak user credential — PBKDF2 slows guessing, it does not make a four-digit PIN strong. That is
  why the credential only protects a wrapping, and why attempt limits and lockout policy belong to
  the authentication layer.

## Android 9 (API 28) compatibility

- Every primitive used here is available from API 28: `AES/GCM/NoPadding`, `PBKDF2WithHmacSHA256`,
  `HmacSHA256`, `SecureRandom`, `KeyGenParameterSpec` and `KeyPermanentlyInvalidatedException`.
- No API 29+ call is used, so there is no version branch that could silently weaken an older device.
- `EncryptionContext.entries` and other Kotlin 1.9+ language features are compile-time only.
- GCM nonce size (96 bits) and tag size (128 bits) are fixed in the format, not chosen per device.

## What this layer deliberately does not do

- No credential verification: `KeyDerivationService` derives keys, it does not decide whether a
  credential is correct. Comparison belongs to the authentication layer.
- No persistence of any cryptographic material: no preferences, no database, no files. Storing
  parameters (salt, iteration count, wrapped keys) is a storage decision for the layers that own the
  data, and the raw recovery key must never be stored at all.
- No streaming/chunked file encryption: `EncryptionService` is for small payloads (it refuses
  envelopes larger than 32 MiB). The vault chunks files and reuse this interface per chunk.
- No PIN enrolment, biometric prompts, lockout policy or session handling.

## Verification

- **Independent known-answer vectors.** `tools/crypto_reference.py` re-implements the envelope
  format and PBKDF2 in Python/OpenSSL; the generated fixtures are embedded in the JVM tests, so the
  Kotlin code is checked against a second implementation rather than against itself. That reference
  is how a real bug was caught during development: the first version of the specification
  authenticated only the first five header bytes, which left the purpose tag outside the
  authenticated data.
- **Standard vectors.** HKDF is tested against RFC 5869 appendix A (cases A.1–A.3), PBKDF2 against
  the published PBKDF2-HMAC-SHA-256 vector.
- **JVM tests** cover all format, maths and policy logic; see `app/src/test/java/.../data/security`.
- **Device tests** cover the Android Keystore: key generation, non-exportability, invalidation,
  deletion and use through a cipher. They run with
  `./gradlew :app:connectedDebugAndroidTest` and are never simulated on the JVM.
